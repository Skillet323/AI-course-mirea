## 2. Постановка задачи и контекст

Проект решает задачу автоматической обработки аудиозаписей совещаний. Пользователь загружает запись встречи, после чего система:

- преобразует аудио в текст;
- выделяет поручения и action items;
- определяет ответственных;
- сохраняет результат в базе данных;
- показывает метрики и диагностические признаки обработки.

Потенциальный пользователь — сотрудник или аналитик, которому важно быстро получить краткий и структурированный итог совещания без ручного протоколирования.

### Формулировка задачи в терминах ML/ИИ

В проекте используются несколько связанных задач:

- **ASR**: преобразование аудио в текст;
- **speaker diarization**: разделение реплик по спикерам;
- **information extraction**: извлечение задач из транскрипта;
- **entity/role matching**: сопоставление задач с участниками.

Ограничения:
- шумные записи;
- перекрывающиеся реплики;
- нестабильное качество аудио;
- неявная формулировка поручений;
- возможные rate limits на внешних LLM API.

### Целевые метрики качества

Используются:
- **WER** и **CER** — качество распознавания речи;
- **Task Precision**, **Task Recall**, **Task F1** — качество извлечения задач;
- **Assignee Accuracy** и **Deadline Accuracy** — точность атрибутов задач;
- **latency** и вспомогательные диагностические признаки — для анализа поведения пайплайна.

### Предобработка и EDA

На этапе подготовки данных выполнялись:

- приведение к единой частоте дискретизации;
- транскрибация;
- анализ качества распознавания;
- сравнение output по gold-разметке;
- проверка распределения количества задач по встречам.

Наблюдения:

- при слабом качестве ответа LLM нужны строгие фильтры и fallback-логика.

## 4. Модели и подходы

### Базовые модели и подходы

В проекте использовались:
- Whisper для ASR;
- pyannote / resemblyzer для diarization;
- rule-based fallback для выделения задач;
- OpenRouter-модели для извлечения задач.

### Улучшения и эксперименты

В ходе доработки были добавлены:
- recursive parser для ответа LLM;
- фильтрация meta-output;
- conservative mode для коротких/шумных записей;
- проверка согласованности задачи с транскриптом;
- speaker aliases для замены `SPEAKER_XX` на имена;
- ручная корректировка спикеров в UI;
- диагностика `task_provider`, `task_parse_stage`, `fallback_used`, `has_diarization`.

### Нейросетевые модели

Для ASR используется Whisper.  
Для извлечения задач сравнивались разные OpenRouter-модели.  
Diarization строится либо на pyannote, либо на fallback на resemblyzer.

## 5. Экспериментальный протокол и результаты

### Экспериментальный протокол

Сравнение моделей выполнялось на одном и том же наборе встреч.  
Для оценки использовались gold-аннотации.  
Результаты сохранялись в CSV и JSON.

### Сравнение моделей по метрикам

Ниже приведены только модели, для которых был получен хотя бы один успешный результат.

| Модель / конфигурация | Успешных встреч | Всего встреч | Task F1 | Precision | Recall | Assignee Accuracy | Deadline Accuracy | Комментарий |
|---|---:|---:|---:|---:|---:|---:|---:|---|
| `inclusionai/ling-2.6-1t:free` | 7 | 13 | 0.3865 | 0.3631 | 0.4286 | 0.3000 | 0.2000 | Наиболее стабильный вариант |
| `openai/gpt-oss-120b:free` | 3 | 13 | 0.2222 | 0.1667 | 0.3333 | 0.0000 | 0.0000 | Работает, но слабее лидера |
| `nvidia/nemotron-3-super-120b-a12b:free` | 4 | 13 | 0.0278 | 0.0167 | 0.0833 | 0.0000 | 0.0000 | Низкая полезность |
| `poolside/laguna-m.1:free` | 2 | 13 | 0.2500 | 0.2500 | 0.2500 | 0.0000 | 0.0000 | Нестабильная статистика |
| `poolside/laguna-xs.2:free` | 1 | 13 | 0.6667 | 1.0000 | 0.5000 | 1.0000 | 0.0000 | Сильный единичный прогон, но выборка мала |
| `baidu/qianfan-ocr-fast:free` | 4 | 4 | 0.2500 | 0.5000 | 0.1667 | 0.5000 | 0.0000 | Короткий прогон, вспомогательный ориентир |

### Выбор финальной модели

Наиболее практичным выбором для извлечения задач является `inclusionai/ling-2.6-1t:free`, потому что она дала лучший баланс между числом успешных встреч и качеством метрик.  
`openai/gpt-oss-120b:free` можно использовать как альтернативу для перепроверки.  
Модели с очень малым числом успешных прогонов нельзя считать надёжно лучшими без расширения выборки.

### Интерпретация результатов

- транскрипция работает устойчиво, но на шумных и длинных записях качество заметно падает;
- извлечение задач пока слабее транскрипции;
- модель часто выдаёт больше задач, чем содержится в gold;
- поэтому важны strict filters, fallback и evaluation loop.

## 6. Архитектура решения и сервис

Пайплайн проекта:

1. загрузка аудиофайла;
2. preprocessing;
3. ASR;
4. diarization;
5. speaker transcript;
6. task extraction;
7. assignment engine;
8. сохранение в БД;
9. оценка по gold;
10. отображение в интерфейсе.

### API и endpoints

Основные endpoints:

- `POST /api/upload_meeting`
- `GET /api/meeting/{id}`
- `GET /api/meeting/{id}/progress`
- `GET /api/meeting/{id}/export`
- `GET /api/metrics`
- `GET /api/stats`
- `GET /api/evaluations`
- `POST /api/evaluate/meeting/{id}`
- `GET /api/health`

### Технологический стек

- backend: FastAPI, SQLModel;
- ASR: Whisper;
- diarization: pyannote / resemblyzer fallback;
- task extraction: OpenRouter + rule-based fallback;
- frontend: React + Vite;
- контейнеризация: Docker;
- хранение: SQLite/PostgreSQL.

## 8. Ограничения и дальнейшая работа

Ограничения проекта:
- diarization может ошибаться на шумных файлах;
- извлечение задач зависит от качества LLM-ответа;
- отдельные модели OpenRouter ограничены rate limit;
- evaluation по gold не покрывает все возможные сценарии.

Дальнейшее развитие:
- ручная правка speaker-меток в UI;
- расширение графиков и dashboard;
- улучшение assignment logic;
- более стабильная модель extraction;
- дополнительные наборы данных для оценки.
